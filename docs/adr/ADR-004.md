# ADR-004: RLS via auth.professional_id() para tenant isolation

**Status:** Aceito
**Data:** 2026-11-02

## Contexto

O Mani é multi-tenant: cada profissional (nail designer/estúdio) deve acessar apenas seus próprios dados (agendamentos, clientes, financeiro). Precisamos de isolamento garantido no banco, sem confiar apenas no filtro de aplicação.

## Decisão

Usar **Row Level Security (RLS) do Postgres no Supabase** com função helper `auth.professional_id()` que extrai o `professional_id` dos claims JWT (`request.jwt.claims`).

## Consequências

**Positivas:**
- Isolamento aplicado no nível do banco: mesmo que o frontend tenha bug, não vaza dados entre tenants.
- Policies declarativas em SQL (`professionals_isolation`, `clients_select`, etc.) versionadas em `packages/supabase-schema/migrations/001_initial_schema.sql`.
- Service role (backend/webhooks) bypassa RLS para operações de servidor (webhooks Asaas/Evolution, sync offline).
- Supabase Realtime herda o mesmo filtro de tenant via canal filtrado por `professional_id`.

**Negativas/Riscos:**
- Todo JWT deve incluir claim `professional_id` (garantido pelo Auth Hook / Edge Function no signup).
- Erro de configuração do claim quebra todas as queries (mitigado por testes de RLS com `SET LOCAL request.jwt.claims`).
- Queries complexas entre tabelas precisam de policies em ambas as extremidades (ex: `appointment_photos` valida via `appointments`).

## Alternativas consideradas

**Isolamento apenas na aplicação (WHERE professional_id = ? no código):** Simples, mas depende de cada query do frontend/backend estar correta; não protege contra erros de código nem acessos diretos ao banco. Rejeitado por segurança crítica de dados de clientes e financeiro.

**Schemas separados por tenant (Postgres schemas):** Isolamento físico, mas operacionalmente complexo (migrações por tenant, conexões dinâmicas). Overhead desnecessário para o estágio atual. Rejeitado.
