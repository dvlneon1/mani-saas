# ADR-001: Supabase vs Firebase (BaaS)

**Status:** Aceito
**Data:** 2026-11-02

## Contexto

O Projeto Mani precisa de um backend-as-a-service que forneça autenticação, banco de dados, storage, realtime e edge functions com baixo overhead operacional, já que o time é pequeno e o foco está no frontend (mobile + web). Os candidatos principais são Supabase e Firebase.

## Decisão

Adotar **Supabase** como BaaS principal.

## Consequências

**Positivas:**
- PostgreSQL nativo com RLS (row level security) — isolamento de tenant via `auth.professional_id()` sem código extra no backend.
- SQL relacional adequado para agendamentos, financeiro e estoque (consistência transacional).
- Realtime nativo sobre PostgreSQL (replicação via websocket) para atualizações de agenda.
- Edge Functions (Deno/TypeScript) para webhooks Asaas/Evolution e lógica de servidor.
- Storage com buckets privados e signed URLs para fotos/PDFs/assinaturas.
- CLI oficial (`supabase`) para migrações versionadas, integrado ao pacote `supabase-schema`.

**Negativas/Riscos:**
- Ecossistema menor que o Firebase para mobile (menos tutoriais RN específicos).
- Realtime depende de conexão estável; offline-first depende da camada MMKV (ADR-005).
- Custo de projeto cresce com uso de Realtime e Edge Functions em escala (monitorar quotas).

## Alternativas consideradas

**Firebase (Firestore + Auth + Cloud Functions):** NoSQL menos adequado para financeiro/agendamento transacional; ausência de RLS equivalente granular por tenant sem camada de aplicação extra. Rejeitado por modelagem relacional ser mais adequada ao domínio.
