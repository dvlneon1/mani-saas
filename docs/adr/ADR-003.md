# ADR-003: NativeWind v4 vs Styled Components

**Status:** Aceito
**Data:** 2026-11-02

## Contexto

O Design System do Mani (40+ componentes, motion, brand, Figma sync) precisa de uma solução de styling que funcione simultaneamente no React Native (mobile) e Next.js (web), com tokens de design (cores, tipografia, spacing) e variantes de componente.

## Decisão

Adotar **NativeWind v4** (Tailwind CSS para React Native) como styling primário do design system e mobile, com Tailwind CSS v4 no admin-web.

## Consequências

**Positivas:**
- Mesma utility-first API no mobile e web (classes Tailwind compartilhadas entre `@mani/design-system`, `apps/mobile` e `apps/admin-web`).
- Tokens em `tokens.json` mapeados para `tailwind.config.ts` — single source of truth de design.
- class-variance-authority + clsx + tailwind-merge para variantes de componente (ex: `btn-primary`, `btn-destructive`).
- Build time zero no RN (NativeWind compila no Metro), bom para iteração rápida no Expo.

**Negativas/Riscos:**
- Styled Components oferece theming dinâmico mais simples em runtime; NativeWind exige regeneração de stylesheet para trocar tema (light/dark) — mitigado por light-mode default (ADR-007).
- Curva de aprendizado de Tailwind para membros do time vindos de CSS-in-JS.

## Alternativas consideradas

**Styled Components:** Excelente para web, suporte limitado e pesado no React Native (estilos em runtime). Não atende bem o requisito de compartilhamento mobile/web. Rejeitado.
